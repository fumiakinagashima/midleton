# Midleton
AIファーストでGenerative UIライクなCRM/SFA。
主な構成としては、SveltekitベースのWEBアプリ + AI API(Claude AIなど) + MCPサーバー。
UIはチャットベース。入力や編集はチャットでの入力ではなく、FORMを生成してユーザー自身が登録を行う。
100%完全なGenerativeUIというよりは、Sveltekitで作成したUIライブラリ（デザインシステム）を用いて必要に応じて構築する。ユーザー自身でFORMやTABLEを定義しない。
つまり、TUI + 動的UIを使ったSPAノーコードのようなもの。
チャットベースの業務画面以外に、設定画面、テンプレート管理画面などがあり、こちらはAIを介さずDBに直接登録する。

## ユースケースサンプル
**ケース1**
ユーザー「顧客情報を登録したい」
チャット「<FORMのHTMLを返す>」
ユーザー「<登録作業>」
チャット「<APIを用いてDBへ登録>, 顧客ID:xxxx で登録しました。」

**ケース2**
ユーザー「今月完了した案件一覧を見せて」
チャット「<APIを用いてDBからデータを取得>, <案件情報一覧を表示するTableのUIを返す>, status = 'complete', complete_date = '2026/6/1 - 2026/6/30'のデータ一覧です。64件」


## 既存業務システムとの比較

**既存システムのUXフロー**
ログイン → 意味のないダッシュボード → 一覧画面に遷移 → 検索 → 詳細ページ（不要な情報も表示）

**Midletonのフロー**
ログイン → 「この顧客の詳細情報ちょうだい」 → レスポンス

既存システムの主な不満点：
- 1つのことをやるために、いくつものページを移動しないといけない
- 1画面に詰め込むと、どこに何があるかわからなくなる
- 不要な機能が多く、必要な操作を逐一調べないといけない
- 基本的なユースケースでも、カスタマイズやプラグインが必須

Midletonはこれらをすべてチャットという単一のインターフェースで解消する。
またDBアクセスは「必要なデータだけを取る」構造になるため、従来のページ単位の全件取得に比べてインフラ負荷も軽量になる。


## 競合優位性

Salesforce・HubSpot・kintoneクラスの企業が技術的にこの構成を作れないわけではない。
しかし、彼らには**作らない理由が山ほどある**。

- 既存ユーザーは現在のUIに慣れており、「チャット画面だけになります」とは言えない
- AppExchangeのようなエコシステムや機能ティア課金モデルが崩壊する
- 彼らのAI戦略（Agentforce等）は「既存UIの上にAIを乗せる」構造であり、UIをAIで置き換えることは構造上できない

これはクレイトン・クリステンセンの「イノベーターのジレンマ」そのものである。
Midletonの優位は技術的な革新性ではなく、**最初からこのパラダイムで作る意思決定の優位**にある。


## インフラ方針

現時点では Cloudflare（D1/KV/R2/Queue/Workers）を採用する。エッジ展開・サーバーレス・低コストという点で PoC に最適なため。

ただし、パートナーの都合（AWS・GCP・Azure 等）によりインフラを変更する可能性を考慮し、以下の原則を守る。

- **DB アクセスは DrizzleORM を通じてのみ行う**（D1 固有の API を直接叩かない）。DrizzleORM は PostgreSQL・MySQL 等にも対応しており、アダプタ差し替えで移行できる。
- **ストレージ・キュー・KV は抽象化レイヤー越しにアクセスする**（将来的に）。現時点は Cloudflare 直呼びで可。
- **ランタイム固有の API（`caches`・`waitUntil` 等）への依存は最小限にする**。

現在は PoC として Cloudflare に直接依存する実装で進め、インフラ移行が現実的になった段階でリファクタリングする。

## データモデル方針

CRM/SFAとして必要なコアエンティティ（顧客・案件等）は固定スキーマで定義する。
「ノーコード」の範囲はUIの自動生成であり、ユーザーがフォームやテーブルのレイアウトを設定しないことを指す。

ただし、コアエンティティに対してユーザーが項目を追加定義できるカスタムフィールド機構を将来的に導入する。
これにより、kintone的な柔軟性をベースに持ちながら、AIによるUI自動生成との組み合わせで差別化する。

```
customers (固定コアカラム)
  + custom_field_definitions (ユーザー定義のフィールドメタ情報)
  + custom_field_values (ユーザー定義フィールドの値)
```

## 将来的な拡張
- 定期実行処理：完全フリーではなく、メール送信・APIコール・データ集計・データ更新など決まった操作を組み替える形に限定。JSON検証で安全性を担保する。AIがノードUIの設定をサポートする。
- 外部API連携：AIを介さず設定画面でAPI連携設定を追加。MCPサーバー経由で秘匿情報にアクセスせずコールできる構成にする。
